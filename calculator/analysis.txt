1. The declaration (prototype) of computeAdd is in mathOps.h, and its definition is in mathOps.cpp. main.cpp only calls it after including mathOps.h.

2. After selecting Addition, main first calls getValues(first, second), which reads both operands through reference parameters (internally it uses readInteger to validate each one). Only if getValues returns true does main call computeAdd(first, second). computeAdd performs the operation with static_cast<long long>(first) + second, calls displayResult to show the operands and the result, and then calls pressAnyKey("Done!") to pause until Enter. Control then returns to the while loop in main, which shows the menu again.

3. main.cpp only contains the calls. The definitions of computeAdd, computeSub, computeMul and computeDiv are in mathOps.cpp, and getOptionFromUser, getValues, displayResult and pressAnyKey are defined in utils.cpp. The headers make the prototypes visible to the compiler, but the linker needs the compiled code of all three .cpp files to connect each call with its definition. When I compiled only main.cpp, the linker reported "undefined reference" errors for computeAdd, getValues, pressAnyKey and the other functions.

4. The include guard (#ifndef UTILS_H / #define UTILS_H / #endif) prevents the contents of utils.h from being processed more than once in the same compilation unit. mathOps.cpp, for example, includes utils.h; if the header arrived twice through different includes, its declarations would be repeated, which can cause redefinition errors.

5. -std=c++17 selects the C++17 language standard. -Wall turns on a broad group of common warnings. -Wextra adds more warnings that -Wall does not include. -pedantic reports code that does not follow the selected standard, including compiler extensions. -o sets the name of the output executable. When the program has only one .cpp file, only the list of source files changes: it names one file instead of three, while the flags and -o stay the same.
